## 2. レビュー対象の目的

「親のもしもナビ」は、親の介護やもしもの時に備え、家族が日記、プロフィール、確認リスト、書類の所在、家族共有、AI相談を1人分の手帳にまとめるWeb/PWAです。

今回のモニターの目的は次の5点です。

1. 40〜60代が説明を受けずに初回登録できるか。
2. 7日間、1日1回の記録を続けられるか。
3. 保存した記録を後から見つけられるか。
4. 確認リスト、書類メモ、家族招待、AI相談の場所と用途を理解できるか。
5. 継続利用、家族共有、Family Plus（月980円・年9,800円）に価値を感じるか。

想定モニターは3人、報酬は1人2,000円（検収後）です。

## 4. モニターの体験フロー

```text
/monitor
  ↓ 「7日間のテストを始める」
/start?monitor=1
  ↓ 端末内にstartedAtを保存
呼び名・関係・都道府県・市区町村・状況を入力
  ↓
/home
  ↓ 7日間、毎日1回記録
確認リスト・書類メモ・家族招待・AI相談を試す
  ↓ 開始から168時間
手帳上部に最終アンケート案内
  ↓
/monitor/report
  ↓ 回答前にスクショ3枚をアップロード
回答本文を送信
  ↓
端末内にreportSubmittedAtを保存
管理画面で回答・スクショを確認
```

### 開始・再開・リセット

- `/start?monitor=1` で端末内 `localStorage` の `oyano_monitor_session_v01` に `startedAt` を保存する。
- 既存モニターセッションと手帳が同じブラウザにあれば、`/start` から既存の `/home` へ戻す。
- `/start?reset=1&monitor=1` は確認後、端末内のテスト用手帳を消し、開始時刻も作り直す。
- 通常の「テストを始める」は既存手帳を自動削除しない。

### 7日間の判定

- `7 * 24 * 60 * 60 * 1000`、つまり開始から正確に168時間後に回答可能になる。
- カレンダー日単位ではない。例: 火曜10:00開始なら、翌週火曜10:00以降に開く。
- 進捗表示は最大「7日目」。残り日数は残りミリ秒から切り上げる。
- 1分ごとに進捗を更新する。
- 7日経過前は `/monitor/report` を直接開いてもフォームを表示しない。
- `?preview=1` は確認専用で、送信ボタンとsubmit処理の両方を止める。

### 日々の課題

- 初日: 親の呼び名、関係、都道府県、市区町村を入れて手帳を1冊作る。
- 7日間: 1日1回「今日の記録」を保存（合計7回）。
- 期間中: 保存した記録を見返す。
- 期間中: 確認リスト、書類の所在メモ、家族招待、AI相談を各1回試す。
- 最終日: 約15分の回答と、気になった画面のスクリーンショット3枚を提出する。
- すべて架空データでよいと案内している。

## 6. 回答と画像のデータフロー

### 回答API

- `POST /api/monitor-feedback`
- 公開API。1時間5回のrate limit。
- 必須文字項目、長さ、画像pathが3件あることをサーバーで検証する。
- 回答は `audit_logs` に `action = monitor_feedback_submitted` として保存する。
- `formVersion = 2026-08-24-7day` を保存する。
- モニターセッション、開始時刻、168時間経過、日記7件はサーバーでは検証しない。

### 画像API

- `POST /api/monitor-feedback/screenshot`
- 公開API。1時間12回のrate limit。
- `home-photos` private bucketの `monitor-feedback/YYYY-MM/{uuid}.{ext}` へ保存する。
- 回答本体には公開URLではなくStorage pathだけを保存する。
- 3枚を並列アップロードした後、回答本文を送る。

### 管理画面

- `/api/admin/monitor-feedback` は管理者認証必須。
- `audit_logs` の最新500件を取得する。
- 画像は管理者認証後だけ、1時間有効の署名URLを作る。
- 管理画面の集計は総回答、7日利用、7日すべて記録、支払意向あり。
- 行動ログと突合せず、回答者の自己申告を集計する。

## 8. レビュー前から確認できている論点

以下は結論ではなく、Claudeに優先度と修正要否を判断してほしい論点です。

### A. 調査設計・測定

1. 7日経過だけで回答フォームが開き、日記7件や課題実施はgate条件ではない。
2. 完走、日記回数、機能試行は自己申告で、実際の端末内記録とは突合しない。
3. 3人という小標本で「3人中2人」を合否基準にしている。
4. 報酬検収条件と「使えなかったことも重要」という方針が、回答者には矛盾して見える可能性がある。
5. 「約15問・15分」と案内するが、画面上は必須15項目に加えて複数選択、自由記述3件、画像3枚がある。
6. 毎日の自然な再訪を測りたい一方、アプリ内に毎日の課題を明示するため、通常利用とは行動が異なる。

### B. 端末・継続性

1. 開始時刻、送信済み状態、手帳は同じブラウザのlocalStorageに依存する。
2. 履歴削除、プライベートブラウズ、別ブラウザ、機種変更で進捗を失う。
3. 開始から168時間のため、利用者が想像する「7日目の夜」ではまだ開かない場合がある。
4. 端末時計を変更するとクライアント側の7日判定も変わる。
5. クラウドワークスの表示名は自由入力で、同サービスとの自動照合がなく、入力間違いや表記揺れが起こり得る。

### C. アンケート設計

1. 「今後も使いたい」「家族共有」「支払意向」が連続し、肯定方向へ誘導する可能性がある。
2. 支払意向は980円/9,800円の提示後の選択で、自由価格や「機能次第」の分解がない。
3. 各機能で「使わなかった」「必要がなかった」という選択肢が不足している。
4. 「見つけられなかった」と「必要だと思わず探さなかった」を区別しにくい。
5. 3枚必須のスクショが、最も困った人や技術に不慣れな人の送信離脱を増やす可能性がある。
6. 自由記述は任意なので、否定理由の深掘りが取れない回答も成立する。

### D. 実装・データ

1. クライアントの7日gateを迂回して公開APIへ直接POSTできる。APIは経過時間を検証しない。
2. 画像3枚を先に保存するため、回答の検証・保存に失敗すると孤立画像が残る可能性がある。
3. 回答を専用研究テーブルでなく汎用 `audit_logs` に保存する。保持期間・削除方法・検収状態の列はない。
4. `crowdworksName` の重複、再送、同一人物の複数回答をサーバーで防がない。
5. 画像APIは認証不要で、rate limitと形式・容量制限が主な防御。
6. 回答送信後の端末内マーク保存に失敗すると、サーバー送信は成功していても再度フォームが出る可能性がある。

### E. 文書と実画面の不一致

1. `/monitor` はAI相談を期間中の課題に含めるが、`docs/TEST_COOPERATION_REQUEST.md` の募集文・LINE文ではAI相談が課題一覧にない。
2. 運営資料の一部は「3機能の試行」と書くが、実画面は確認リスト・書類メモ・家族招待・AI相談の4機能を確認する。
3. 過去の資料には「記録3回以上」の表現が残る箇所があり、現行仕様は7日すべての記録。
4. 管理画面のリンク「回答フォームを見る」は通常URLなので、7日前の管理者にもフォーム本体が見えない。確認用URLは別途追加済み。
