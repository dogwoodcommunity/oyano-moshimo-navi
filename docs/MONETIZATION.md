# 収益モデル設計

最終更新: 2026-08-23
状態: 設計確定・実装待ち（実装はこの文書を正とする）

## 決定事項

| 項目 | 決定 |
|---|---|
| プラン構成 | 無料 と Family Plus の**2段だけ**。第3のプレミアプランは作らない |
| 課金単位 | **家族**（`families.plan`）。個人ではない |
| 価格 | **月額 ¥980 ／ 年額 ¥9,800**（オーナー承認済み・2026-08-22。ストアの価格ポイントに¥980が無い場合のみ、最も近い点に合わせてWebも同額に揃える） |
| 相談の体験 | **家族ごとに初回1回無料**。体験ゼロのまま課金の壁を出さない |
| 解約後 | **記録は無料のまま読み返せる**（書き込みと相談だけ止まる）。これを画面に明記する |
| 手帳内広告 | **永久にやらない**。病気・介護・死亡の記録画面には広告を出さない |
| 地域スポンサー枠 | **申請受付は初期から持つ**。掲載・販売開始は審査基準と地域実績ができてから |

### なぜ2段だけか

使う人はほぼ50代で、機械が得意ではない。3択は迷いのもと。
「無料か、Plusか」の1つの判断だけにする。

### なぜ家族課金か

このアプリの価値は家族で同じ手帳を見ることにある。課金も家族単位なら、
きょうだいで割って1人あたり¥250〜500。「親のこと」への支出として妥当な線になる。
DBも最初から `families.plan` で設計されている。

### 招待された家族の扱い

- Plusは家族手帳ごと。手帳を作った人が支払い・招待枠を管理する。
- 招待された家族は、同じ手帳の閲覧・記録・確認リスト・写真更新に参加する。
- 招待された家族に、同じ手帳の追加課金CTAは出さない。
- 招待された家族が自分で別の家族手帳を作る時だけ、自分のプラン判断になる。
- UI文言は「共有された手帳に参加中」「追加課金なし」に統一する。

### なぜ¥980か

- AI相談の原価は約¥13/回。上限（5回/日）まで毎日使われても月¥2,000弱、
  実態は月¥100〜300。¥980ならAppleの手数料15%（Small Business Program）を
  引いた手取り約¥833で吸収できる。
- 固定費（Supabase + Vercel ≒ 月¥7,000）はPlus 9家族で回収できる。
- 年額¥9,800（2ヶ月分お得）を並べるのは、介護が数年続くことと相性がいいため。

### なぜ解約後も読めるようにするか

親の介護は必ず終わる。解約は構造的に起きる。そのとき記録を人質に取ると、
看取りの記録を扱う製品としての信頼が死ぬ。逆に「解約しても読める」は
加入時の心理障壁を下げる（サブスク警戒の50代に効く）。
その家族は次に自分の配偶者や自分自身の番で戻ってくる。

## プランの線引き

| | 無料 | Family Plus |
|---|---|---|
| 親の手帳 | 1人分 | 2人目以降も |
| 家族の招待 | あなたのほかに1人 | 追加できる |
| 日々の記録・タスク | ○ | ○ |
| 危機モード（急なとき） | **○（登録すら不要）** | ○ |
| AI長期相談 | **初回1回だけ** | 1日5回まで |
| 家族会議用PDF・容量拡張・月次ふりかえり | − | ○ |

**危機モードは絶対に課金の壁にしない。** 入院した夜・危篤・死亡直後の
チェックリストは、登録なしで全部使える。ここは信頼と入口であって商品ではない。
不安を煽って売る形は、この製品では一切やらない。

## 課金の入口

| 面 | 決済 | 備考 |
|---|---|---|
| アプリ（iOS/Android） | RevenueCat（IAP） | webhookは実装済み（`api/revenuecat/webhook`） |
| Web | Stripe | checkout実装済み（`api/stripe/plus-checkout`） |

**アプリ内から外部決済へ誘導しない**（ストア審査。`docs/PRIVACY_AND_REVIEW_GUARDRAILS.md` 準拠）。
アプリにはIAPだけを見せる。Webの価格はアプリと同額に揃える。

**価格はすべて税込で揃える。** App Store / Google Play は税込¥980の
価格ポイントで登録し、WebのStripeも税込¥980にする。Webだけ税抜だと不信のもと。

RevenueCatの商品ID（案）: `plus_monthly` / `plus_annual`、
製本PDF単発: `bound_book_once`。
確定した価格は `NEXT_PUBLIC_PLUS_PRICE_LABEL` にも入れる（Webのプラン表示が「準備中」から変わる）。

## 初回相談無料の仕様

対象: `apps/web/app/api/consult/route.ts` の `authorizePlusConsult`（Plusゲート実装済み）。

- `families` に `consult_trial_used_at timestamptz` を1列足す（SQLは `supabase/` に置き、`scripts/run-sql.mjs` で流す）。
- 判定順: ログイン確認 → 家族取得 → **Plusなら通す** → Plusでなく
  `consult_trial_used_at` が null なら**通して、成功応答の直前でマーク**する。
  失敗した相談（API側エラー）で権利を消費させない。
- 使用済みなら 402 `plus_required` を返す（現行どおり）。メッセージは
  「おためし相談は使いました。続きはPlusで使えます。手帳と記録はこのまま無料で使えます。」の趣旨。
- クライアント（アプリ `consult.tsx`）は 402 を受けたらPlus案内を出す。
  おためしが残っている家族には「1回だけ、無料でためせます」と先に見せる。

レート制限（利用者5回/日・全体200回/日）は現行のまま残す。

## 追加機能（オーナー承認済み・2026-08-22）

### A. 緊急カード（無料）

親の冷蔵庫に貼る前提の、**A5一枚の印刷用PDF**。

- 載せるもの: 呼び名／生年月日／今の状態／薬・注意点／かかりつけ（病院・施設）／
  主な連絡先／家族の連絡先。すべて管理手帳の既存項目から組む。
- 載せないもの: 書類の保管場所。紙は家の外に出ることがある。
  （暗証番号等はそもそも保存していない）
- **無料に置く**。獲得装置であって商品ではない。50代とその親は紙で安心する層で、
  冷蔵庫のカードは、まだ使っていない兄弟や親戚の目に入る＝物理的な口コミになる。
- 導線: 管理手帳から「緊急カードを印刷する」。生成はWeb側のPDFでもアプリ内の
  共有シートでも、実装しやすい方でよい。

### B. 手帳を一冊に（製本PDF）— 旅の終わりの商品

日々の記録・写真・タイムラインを、**一冊のPDFにまとめて出力**する。
記録が形見になる。この製品だけが作れる、感情価値が最も高い瞬間の商品。

- 課金: **Plusは無料／無料プランは買い切り ¥980**（IAPは消耗型、Webは
  Stripeの単発決済。税込で揃える）。
- 閲覧自体は無料のままなので、人質ビジネスにはならない。
  「きれいに綴じた一冊」だけが商品。
- 解約後の家族にも買える。「介護が終わると収益もゼロ」への部分的な答え。
- 中身: 表紙（呼び名・期間）／プロフィール要約／タイムライン（写真含む・古い順）／
  家族会議PDFとは別物（あちらは現在形の共有、こちらは記録の保存）。

### C. 役目を終えたら、こちらから解約を案内する

家族の対象者が**全員「完了」ステータス**になったら、プラン画面に案内を出す。

> 役目を終えたようです。Plusを解約しても、これまでの記録はずっと読み返せます。
> 記録を一冊のPDFにまとめることもできます。

- 自動解約はしない。案内だけ。通知は出さない（プラン画面を開いた時だけ）。
- 普通のサブスクは絶対にやらないことだからこそ、信頼の証明になる。
  看取りの後に「気づいたら引き落とされていた」が一番評判を壊す。
- 解約された分は、B（製本PDF）と口コミで回収する設計。

### D. 音声で記録（第一段階は文言だけ）

50代の入力障壁はタップ以下＝しゃべること。ただし専用実装は急がない。

- **第一段階**: 記録画面の補足欄に
  「キーボードのマイクボタンで、話すだけでも書けます」の一文を添えるだけ。
  OSの音声入力で目的はほぼ果たせる。実装コストほぼゼロ。
- 第二段階（後日判断）: 専用の録音ボタン。Expo Goでは動かないため
  開発ビルドが要る。効果を見てから。

## 画面に書く文言（実装時にそのまま使ってよい）

- プラン画面: 「解約しても、これまでの記録はそのまま読み返せます。」
- おためし: 「AI相談を、1回だけ無料でためせます。この人の記録を読んで整理します。」
- 壁（402後）: 「おためし相談は使いました。続きはPlusで。手帳と記録はこのまま無料で使えます。」

トーンは既存に合わせる。急かさない。失うものがないことを必ず添える。

## B2Bスポンサー枠（初期から申請受付だけ持つ）

地域×分野（葬儀、相続士業、家族信託、ホーム紹介、保険、遺品整理など）で
スポンサー枠を切るB2Bモデルは、将来の大きな収益柱として残す。
ただし、これは「利用者の手帳に広告を出す」ことではない。

初期からやること:

- `/sponsors` で、事業者が都道府県・市区町村・分野・希望枠を申請できるようにする。
- 申請は営業リストと枠需要の先行把握として扱う。
- 管理画面で申請内容を確認できるようにする。
- 親御さんの居住都道府県を登録時に取り、県別の有効会員数を管理画面で見られるようにする。
- 都道府県×6分野の掲載枠は最初から管理できるようにする。

初期からやらないこと:

- 手帳、記録、危機モード、AI相談の途中に広告や事業者名を出す。
- 審査前の事業者を利用者へ紹介する。
- 成約課金や送客課金を始める。

掲載・販売を始める条件:

- 地域ごとに会員密度ができていること。
- 掲載基準、審査基準、苦情対応、問い合わせ計測が決まっていること。
- 1枠あたり月何件の問い合わせが来るかを説明できること。

つまり、初期実装は「スポンサー枠を売り始める」ではなく、
「将来売るための申請窓口と営業台帳を最初から持つ」という位置づけにする。

### 2026-08-23 P1仕様の確定 — 地域データ設計

登録フロー変更:

- 初回必須入力: 呼び名 + 関係 + 親御さんの居住都道府県。
- 市区町村は任意。従来方針どおり住所詳細は取らない。
- 本人(利用者)の都道府県は任意項目。
- 既存ユーザーには次回起動時に「親御さんの都道府県」入力を1回だけ促す。
  スキップ可で、あとから設定/プロフィールで入力できる。
- 集計・掲載マッチングの基準はすべて「親の居住都道府県」。
  子世代本人の住所では判定しない。

DB:

- `people` テーブルに `prefecture` / `city` を追加する。
  UI上は `prefecture` を必須扱い、`city` は任意扱いにする。
- `prefecture_active_family_counts` ビューで、都道府県別の有効会員数を集計する。
  有効会員は「親情報1件 + 家族1人招待」の既存KPI定義に寄せる。
- `partners` テーブルは `prefecture × category` をユニークにする。
  分野は葬儀、相続士業、家族信託、ホーム紹介、保険、遺品整理の6分野。

会員数の表示:

- 管理画面: 全都道府県の生数字と前月比を常時表示する。
- 公開側(相談先ページ・掲載営業LP): 閾値制にする。
- 有効会員100家族以上の県だけ「◯◯県:△△家族が利用中」を表示する。
- 閾値未満の県は生数字を出さず、「募集中」などの表記に留める。
- 閾値は環境変数 `PUBLIC_PREFECTURE_USAGE_THRESHOLD` で変更できる。

掲載営業用エクスポート:

- 管理画面から「県×分野: 会員数・相談先ページ表示数・タップ数・問い合わせ数」を
  CSV出力できるようにする。
- CSVは営業資料に直貼りする用途。公開表示とは違い、管理者だけが生数字を見る。

## やらないこと

- 手帳内広告。病歴・死亡を扱う画面に広告は出さない。永久に。
- **時間制の無料トライアル（7日間無料など）**。体験ゲートは「初回相談1回無料」に
  一本化する。トライアル終了→自動課金は、うっかり課金への警戒が最も強い50代が
  相手のこの製品では、「急かさない・失うものがない」というトーンと衝突する。
- 第3のプラン。
- 危機モードへの課金の壁。
- アプリ内からWeb決済への誘導。
- 事業者紹介の送客課金・成約課金。スポンサー枠の申請受付だけは初期から持つが、
  ユーザー手帳内表示・紹介・送客課金は、審査基準と地域実績ができるまでやらない。

## 将来の柱（スポンサー申請は初期受付、掲載・送客は後で判断）

1. **B2B（企業の福利厚生）**: 2025年の法改正で企業に介護両立支援が義務化された。
   50代社員向け施策として企業契約（月額/人）。解約問題がなく単価が安定する。
   個人課金が回り始めたら本命。
2. **事業者紹介**（葬儀・士業・遺品整理): `providers` / `referrals` /
   `consent_to_provider_share` のテーブルは既にある。単価は大きいが、
   要配慮情報×紹介料は信頼を一撃で壊しうる。明示同意・審査済み事業者・
   AIは事業者名を出さない、の縛りを守れる体制ができるまで凍結。
3. **地域スポンサー/掲載枠**: 申請受付は初期から始める。
   実際の掲載・販売・送客は、地域密度と審査基準ができてから判断する。

   地域×分野（葬儀、相続士業、家族信託、ホーム紹介、保険、遺品整理など）で
   枠を切るB2Bモデル。ただしこれは「病歴・死亡を扱う画面に広告を出す」ことではない。
   手帳、記録、危機モード、AI相談の途中には出さない。ユーザーが明示的に開く
   地域ガイド、相談先一覧、印刷物の協賛枠など、文脈が分かる場所だけを将来検討する。

   枠の価値は地域の会員密度で決まる。全国のスポンサー枠は最初から申請受付できる
   ようにしておくが、公開する会員数と営業資料に使う数字は閾値制にする。目安として、
   1地域1分野の広告主が月3万円を払い続けるには、2〜3か月に1件以上の問い合わせ実績が
   必要。会員密度が出た県から順に営業し、「1枠あたり月何件問い合わせが来たか」を
   示せる県を増やしていく。

## 実装タスク（Codex向け・この順で）

1. `supabase/consult_trial.sql` — `families.consult_trial_used_at` 追加。
   `scripts/run-sql.mjs` で流せる形にする。
2. `authorizePlusConsult` におためし判定を足す（上記仕様）。
   マークは相談成功時のみ。
3. アプリ `consult.tsx`: 402（`plus_required`）の受け皿と、おためし残の案内表示。
   おためしが残っているかは、402が来る前に分かる形が望ましければ
   `/api/consult` にGETを足すか、家族情報に含める（実装しやすい方でよい）。
4. 価格の確定作業: RevenueCatに `plus_monthly` / `plus_annual` を登録、
   Stripeに同額のPrice作成、`NEXT_PUBLIC_PLUS_PRICE_LABEL` 設定。
5. プラン画面（Web `plans/page.tsx`・アプリ `account/plan.tsx`）に
   「解約しても読める」の一文と、無料/Plusの線引き表を反映。
6. 記録画面に「キーボードのマイクボタンで、話すだけでも書けます」の一文（追加機能D第一段階）。
7. 緊急カード（追加機能A）。管理手帳から印刷用A5 PDFを出す。
8. 完了時の解約案内（追加機能C）。全対象者が「完了」の家族のプラン画面にだけ出す。
9. 製本PDF（追加機能B）。Plusは無料、無料プランは買い切り¥980。
   生成の重さ次第でWeb側生成でよい。

1〜5が最優先（課金の土台）。6〜8は安いので同じ弾で。9は中期でよい。

受け入れ条件:
- 無料家族が相談を1回成功させると、2回目から402になる。
- 相談APIがエラーを返した回では権利が減らない。
- Plus家族は今までどおり1日5回まで。
- 危機モードは未ログインで全ページ開ける（現状維持の確認）。
- 緊急カードに書類の保管場所が載っていない。
- 解約案内は、完了していない家族には一切出ない。
- `apps/mobile` と `apps/web` の `tsc --noEmit` が通る。
