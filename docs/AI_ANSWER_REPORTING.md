# AI回答の報告と運営確認

2026-09-21。ローカル実装・合成試験の記録。配信・本番受付・審査適合の確認ではない。

## 利用者の操作

Nativeの保存済みAI回答と相談履歴に「このAI回答の問題を報告」を表示する。理由を1つ選び、運営担当者が保存済みの相談文・回答を確認し得る説明へ同意してから送る。画面を開く、回答を生成する、理由を選ぶだけでは送信しない。メール等の別アプリは開かない。

送信はBearer認証付き `POST /api/consult/report`。本文は `{ turnId, reason }` だけ。理由は `unsafe / inappropriate / incorrect / other`。回答本文・相談文・氏名・対象者ID・家族IDは送らず、余分なキーは拒否する。運営への報告は相談の安全性改善のためであり、相談内容への個別回答や緊急対応を約束しない。

サーバーはログインを確認し、保存済み回答→非公開相談スレッドの所有者→対象者→現在の家族所属を検証する。他の家族メンバーの相談、削除済み回答、権限喪失後の相談は受け付けない。読込障害と保存障害は成功表示にしない。受付確認前に通信が途切れた場合は未確認と表示し、再送可能。同じ利用者・回答は最初の理由のまま1件だけ保存する。

## 保存と削除への整合

既存 `audit_logs` に `action = ai_consult_answer_report`、`target_type = ai_consult_turn`、`target_id = turnId` を保存する。IDはサーバー側の決定的UUIDで、既存主キーにより並列再送も重複しない。metadataは理由と説明版 `ai-answer-report-v1-2026-09-20` のみ。利用者IDは `actor_user_id` のみに置き、metadataや本文コピーへ埋め込まない。

既存のアカウント削除では `actor_user_id` がNULLになり、本人の非公開相談スレッド・回答は削除される。報告ログの理由・回答IDは既存監査ログとして残るが、削除された本文をこの機能から復元しない。相談履歴だけを削除した場合も本文コピーは残らない。専用の保管期間・自動削除ジョブは追加していない。既存RLSは監査ログの閲覧を `is_app_admin()` に限定し、通報APIから他の報告一覧は返さない。

## 運営確認画面と権限

`/admin/ai-reports` を追加した。既存 `app_admins` のallowlistとSupabase本人Bearerを毎回検証し、一覧・本文閲覧・状態変更のすべてにAAL2を要求する。AAL1で利用できるのは自分の認証状態確認と既存のMFA追加確認だけ。静的管理キー・削除専用実行者・一般利用者では通報を読めない。新しい管理者行やroleの追加、既存roleの変更、管理者への権限付与はしていない。削除専用の設定画面へ誘導しない。

一覧APIは `GET /api/admin/ai-reports?offset=0`。20件ずつ、受付番号・理由・受付日時・対応状況のみを返す。報告者の氏名・IDや相談本文は返さない。「この1件を確認」を押した場合だけ `GET /api/admin/ai-reports/{reportId}` で、その通報の回答IDと報告者本人の非公開スレッド所有権・現在の対象者/家族権限・通報同意版を確認して、相談と回答1件を返す。任意のturnIdで本文を指定するAPIはない。削除済み・報告者の参照解除済み・所有権/同意を確認できない場合は本文を表示しない。本文の一括取得・出力・別媒体へのコピー機能は設けていない。

本文を返す前に、閲覧した運営担当者・通報ID・本文の有無を `audit_logs` の `ai_consult_answer_report_viewed` として保存する。保存の確認に失敗した場合は本文を返さない。画面上の本文はReactのメモリだけに置き、ログアウト・認証変更・別タブでの認証変更・ページ非表示で消す。これらの変更後の遅延応答も破棄する。レスポンスは `private, no-store`。サービスロール鍵はブラウザへ渡さない。

## 対応状況と監査

`PATCH /api/admin/ai-reports/{reportId}` は `expectedRevision / status / outcome` の固定値だけを受け付ける。「確認中」「要対応（危険・誤情報・不適切・その他）」「完了（問題を確認できず・修正と確認済み・本文確認不能）」を記録できる。本文や担当者メールを自由記述欄へ複製しないよう、自由文は受け付けない。

更新は既存 `audit_logs` の `ai_consult_answer_report_review` への追加だけ。担当者は `actor_user_id` FK、対象は報告ID、metadataは版番号・状態・判断のみ。通報IDと版番号から作る主キーで同時更新を競合扱いとし、他担当の結果を上書きしない。同じ担当の同じ送信の再試行は既存の保存を確認して成功を返す。最新状態はJSON数値の版番号で取得し、10版を9版より前と誤認しない。監査担当者のアカウントが削除されても、metadataに担当者の個人情報を残さず、既存FKのNULL化に従う。

対応手順:

1. 正式に指名された既存管理者本人がMFAを確認し、一覧から対象の1件を開く。
2. 「確認中」を保存して調査する。本文をメール・外部AI・チャットへ転記しない。
3. 問題を確認した場合は該当する「要対応」を保存し、既存のレビュー・試験・本番反映手順で必要な修正を行う。状態変更だけで修正が行われたとは扱わない。
4. 修正と検証の完了後だけ「修正と確認済み」を保存する。本文が削除済み等なら「本文削除等により確認不能」、問題を確認できなければ該当する完了理由を選ぶ。自動通知・回答削除・プロンプト変更はしない。

## 申請前に残る運用ゲート

担当者の正式指名、既存app_admins/AAL2での実環境受入、確認頻度と不在時の担当、具体的な保存期間は未確定・未検証。これらは削除対応の既存担当者・保持日数から自動転用しない。報告の理由・閲覧/対応監査の保存期間に該当する現行規定は確認できず、モニター6か月や外部AIの保持日数を通報監査へ適用しない。保管期間の合意と必要な削除運用が決まるまで、通報運用の申請条件は未達とする。

`/legal/privacy` の「本人だけが相談履歴を確認できる」説明に、本人が明示同意した通報調査の限定閲覧という例外と監査記録を追記した。本文コピーなし・削除済み本文を復元しない・監査上の識別情報への参照解除を明示したが、保存期間を勝手に設定していない。法務/運用確認と本番配信は別条件。

DB migration・新規table・本番SQL実行・本番書込・通知送信は未実施。新しいroleやenvも不要。
ローカル合成試験は `node scripts/test-consult-report.mjs`、`node scripts/test-ai-report-review.mjs`、`node scripts/test-ai-report-review-ui.mjs`。Bearer/allowlist/AAL2・正確な所有者と1件の本文・監査保存失敗・削除/権限変更・競合/再試行・画面の遅延応答隔離を確認する。実際のPostgREST/本番RLS・管理者MFA操作・実報告の受入は合成試験と別に確認する。
