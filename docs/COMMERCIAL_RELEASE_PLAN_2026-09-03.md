# 正式商用版からアプリ公開までの実装計画（2026-09-03）

## 方針

11人のモニター結果に従い、最初の商用公開は有料転換を急がず、無料Web版で
「記録する → 見返す → 書類の場所を残す → 家族と共有する → 専用AIへ続けて相談する」までを
安全に完走できる状態を完成条件とする。

順番は次の3段階とする。

1. 無料Web版を正式公開できる品質へ上げる
2. 法務・解約・再送耐性まで揃えてから有料受付を開く
3. 固まったWeb仕様をExpoへ移し、iPhone / Androidを公開する

スポンサー掲載、事業者予約、物理的な製本・配送は、この3段階の完了条件に含めない。

### Stage Aの完了判定

- 新規利用者がカード登録なしで1人分の手帳を作り、保存・復元・家族共有まで完走できる。
- 別家族、viewer、未認証者が書き込み・写真upload・通知送信・AI記憶変更を行えない。
- 利用者が、自分のデータの保存範囲、共有範囲、削除方法を画面上で確認できる。
- 未提供機能は「準備中」で止まり、APIも副作用より前にfail closedする。
- CI、本番schema検証、Brave / Safari / Chrome、iPhone / Android幅の実機確認がすべて通る。

既存本番DBへ家族ロール境界を反映する時は、従来の `production_rls.sql` 全体を再実行せず、
対象ポリシーだけを冪等に更新する `supabase/family_role_hardening_20260904.sql` を用いる。

## Stage B — 有料受付

無料版の定着を確認した後に行う。有料受付を開く条件は以下のすべて。

- 特商法の販売事業者、責任者、所在地、電話、問い合わせ、税込価格、提供時期、解約・返金条件を確定する。
- 実際に提供できるPlus機能だけを料金画面へ表示する。
- Stripe live商品・Price・Webhookを設定する。
- Checkoutのfamily指定、owner権限、冪等性をサーバーで保証する。
- Webhookをevent IDで重複排除し、順不同・再送・DB一時失敗でも状態を復旧できるようにする。
- Billing Portalまたは同等の自己解約導線を用意する。
- 解約後も既存の基本記録を読めることを自動試験する。
- テスト決済、更新、支払失敗、解約、返金を本番相当環境で完走する。

特商法情報またはStripe必須設定が1つでも欠ける場合、画面は「受付準備中」、Checkout APIは503で停止する。
すべて揃った場合も自動では開かず、Plusと人的サポートそれぞれの販売安全スイッチを運営が明示的に
`true` にした場合だけ受付を開始する。

## Stage C — iPhone / Androidアプリ

Web正式版のデータ契約と権限を正本にし、別実装を増やさない。

### アプリ公開前P0

- 未設定時のdemo fallbackを配布buildでは禁止する。
- 全Stack routeへ認証gateを付ける。
- 初回family/person作成を、family・role・plan・人数を検証する原子的RPCへ統一する。
- viewer read-only、家族選択、相談履歴private、手帳へ保存したAI回答は家族共有、という境界をWebと一致させる。
- 写真の実upload・削除・復元をWebのStorage policyへ統一する。
- Push許可、token、通知設定、送信receipt、配信停止を実機で確認する。
- iOSはApple IAP、AndroidはGoogle Play BillingをRevenueCat等で統合し、WebのStripe CTAをアプリ内に置かない。
- アカウント削除、家族退出、所有者移管をアプリ内から完走できる。
- Magic Link / deep link、オフライン復帰、機種変更、ストア審査用説明をiPhone / Android実機で確認する。

## 外部確認が必要な項目

次はコードだけでは確定できないため、実行前にユーザーへ内容と影響を示して承認を得る。

- 正式な事業者・問い合わせ・返金情報
- Supabase本番migration
- Resend送信ドメインと実メール送信
- Stripeアカウント、商品、live/test決済、Webhook
- Apple / Googleの契約、税務・銀行情報、IAP商品
- 法務専門家による最終確認
- 本番deployと段階公開
