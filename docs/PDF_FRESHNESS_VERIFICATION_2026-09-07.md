# PDF画面を開いた後の記録変更 — 2026-09-07

## 範囲

追加費用・新規契約なしの継続作業。前日のClaudeレビュー記録で未完了とした
「別画面で記録を変更・削除した後、開いたままのPDF画面へ反映されるか」を確認する。
今回の実装はローカル画面の読取・印刷準備の失効のみで、記録・写真・DBへの書込みを増やさない。
実バックアップ取得、メール送信、有料AI呼出し、契約変更、本番反映は含まない。
追加で、既存の隔離PostgreSQLによる合成復旧試験に、バックアップ後の日記削除の再適用を加えた。
Claudeの新規レビュー送信ではなく、9月6日に受領したレビューの残課題を継続した作業である。

## 原因と修正

変更前は、PDF画面を開く時だけ記録を読み込んでいた。
「PDF保存画面を開く」も最新の保存内容を照合せず `window.print()` を呼び出していた。

- 別タブのstorage変更・画面へのfocus・表示再開時に、対象手帳と日記を既存storeから読み直す。
- 原データが変更された時だけ、印刷準備・進行中の画像待機結果・拡大写真を失効させる。
- 削除receiptを含む既存storeの表示規則を利用し、削除した記録と対象者を除外する。
- 手動で外した選択は維持する。後から追加された記録は、自動でPDF対象にしない。
- 準備の開始時・画像待機後・印刷ボタンの直前でも再確認する。
- 古い写真取得結果は世代・対象者・保存先の一致で制限する。一時的な署名URLの補完だけでは
  原記録の変更と判定しない。再読時に新たな認証・クラウド取得は開始しない。

## 自動回帰

`scripts/test-memory-book-freshness.mjs` は実pageを合成React hook/event環境で動かし、実storeの読取・
削除receiptを使う。`test-memory-book-export.mjs` から呼び出すため、既存CI・Stage Aの対象になる。
合成の印刷関数は呼出し回数だけを数え、OS印刷や実PDF生成は行わない。

- storageイベントを受け損ねても、出力直前の変更を検出して印刷を止める。
- 確認・再準備後、変更がなければ印刷へ進める。色など無関係なstorage変更では失効しない。
- 削除済みraw行が残っても、完了receiptで除外する。未選択・追加記録を勝手に選ばない。
- 画像待機中に手帳が消えても、待機完了後に古い印刷準備を復活させない。
- 表示復帰や全storage削除にも対応し、unmount時はイベントを解除する。
- 準備開始前の変更、認証待機中の削除、署名URL補完後の有効な準備、拡大写真の削除を確認する。
- 古い待機処理が後から終わっても、新しい準備のbusy状態を解除しない。
- 画面更新のcommit前に旧ボタンの処理を呼んでも、古い本文・選択で再準備や出力を認めない。
- 写真のstate更新が遅延し、失効後に適用されても旧URLを戻さない。対象者・写真path・bucketの
  不一致もそれぞれ合成negative試験で確認する。
- 読取・写真補完・印刷で元storageがbyte単位で不変であることを確認する。

## 検証経過

- 初期版 `0259977` に新回帰だけを加えるnegative controlでは、イベントを受け取らず古い内容で
  印刷する試験が `actual 1 / expected 0` で失敗した。修正後は同じ試験が成功した。
- 最初の修正候補で37工程（source33・lint・型2・fresh build）は通過したが、独立レビューで
  「再読でrefを進めた直後、Reactの画面更新前に旧handlerを呼ぶ」競合を合成再現した。
  実ブラウザでの再現ではない。初回合格を最終差分に流用せず追加修正した。
- 画面に描画した世代・準備番号を各handlerが保持し、最新refと違う旧handlerからの操作を拒否する。
  記録変更・選択変更それぞれのcommit前と、commit後の正しい再準備を追加試験した。
- 旧修正候補に追加回帰だけを重ねたnegative controlも、画面commit前の旧handler試験で
  `actual 1 / expected 0` と失敗した（9月7日10:39:56 JST）。最終修正では成功した。
- 最終アプリ差分の隔離37工程（source33・lint・Web/mobile型2・fresh build）が再試行なしで成功、
  10:42:02 JST終了、BUILD_ID `g2SHjC2PdfVK-SfZC5UM_`。
  lintの既存41警告は残る。SQL10はこのローカル37工程に含めず、今回は未変更のため個別再実行していない。
- 実装者以外の最終レビューでP0/P1指摘なし。実page/実storeを使うPDF回帰とdiff-checkも独立再実行PASS。
- 同じ隔離ブラウザの2タブで、架空記録2件から1件を外してPDFを準備した後、別タブの本文を変更・保存。
  PDF画面のreloadなしで新本文と準備取消の警告が表示され、外した1件は未選択のままだった。
  確認後の再準備は成功。別タブで架空の9月7日記録を追加すると、その記録は未選択で表示され、
  選択数1件を維持し、準備も取り消された。ここからの再準備も成功。
- 390px幅で準備画面と注意文を目視確認し、client/scrollWidthとも375px（縦スクロールバー分を除く）、
  横はみ出しなし。OSの印刷画面・実PDF保存は実行していない。
- 作成したローカル検証タブ2つだけを閉じ、viewportをreset。試験サーバーのPID/cwdを照合して停止し、
  10:45:12 JSTに3123の待受0を確認。既存本番/管理/3119のタブには手を加えない。

## 追加の合成復旧試験

`scripts/test-synthetic-recovery.mjs` の固定fixtureだけを拡張した。本番データを入力する汎用復旧ツールではない。

- dump完了後に合成元DBで日記1件を実削除RPCで削除し、後発receiptの完全なidentityを取得。
  旧dumpの隔離復旧先では、その日記が1件存在し、後発receiptが0件であることを確認した。
- 同じfamily/person/localCase/localDiaryに対し、復旧先の現在revision/hashと固定の架空ownerを用いて
  削除RPCを再実行した。receiptを先にinsertする方式ではない。元deleted_atの復元でもない。
- 別家族に同じlocalDiaryIdを持つ記録、既存receipt/job、無関係テーブルは不変。
  2回目の再適用も全行hashが不変。削除済み日記の再insertは40001で拒否された。
- 写真の物理削除は完了扱いにせず、cleanup jobをpendingのまま検査。元dumpのbytesも不変。
- 最終実行は10:46:12.792〜10:46:15.616 JST（backup開始〜受入終了）、56テーブル・467,561-byte dump、
  既存10確認と後発日記receiptの限定再適用がPASS。合成復旧2,565ms、工程全体5,629ms。
  cleanup PASS、試験コンテナ残存0。初回sandbox内はDocker preflightで終了し、資源作成なし。
  その後、限定されたローカルDocker実行で2回成功した。
- 実backup/Auth/Storage、本番の再適用権限/手順、対象者・アカウントの後発削除、本番RPO/RTOは未検証。
  `newerDeletionReceiptReplay: SYNTHETIC_DIARY_ONLY_PASS` とし、全削除の復旧対応完了とはしない。

## 限界と正式公開の残条件

- この端末の保存内容に反映されていない別端末の変更まで、オフラインで検出するものではない。
- 既に保存したPDFや、OS・ブラウザで開いた印刷画面を取り消せない。古い印刷画面を閉じ、
  アプリから準備し直す説明を追加する。ブラウザの直接印刷操作全体を禁止するものではない。
- 実iPhone/Androidの保存先・印刷結果、2端末のクラウド権限・復元は別途必要。
- 実バックアップの保管先、DB/Auth/写真の取得・隔離復旧、問い合わせ受信・運用、法務最終確認は未完了。
- バックアップより新しい削除receiptの復旧時再適用は、上記の合成日記1件だけを確認した。
  本番や対象者・アカウント単位へ一般化しない。PDF表示上のreceipt確認とも別の証跡である。

正式公開の判定は引き続きNO-GO。実バックアップ準備の最小の次の選択は、
既に持っているどの端末・媒体を保管先に使うか。保存先の指定だけで本番取得・外部送信まで承認されたとはしない。
